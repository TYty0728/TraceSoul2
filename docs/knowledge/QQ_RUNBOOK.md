# QQ 回复与照片排障

## 多次回复

先用日志 `TraceId` 和入站 `event=message_id` 区分：

| 现象 | 检查点 |
|---|---|
| 同一个 `message_id` 多次进入收件箱 | OneBot 重放或多 WS 投递；本次已在入队前去重，日志为“QQ 重复消息已忽略” |
| 不同 ID、正文一样 | 可能是用户实际重复发送；不按正文吞消息 |
| 一次输入先说“等一下”，稍后带结果回来 | `KernelLogic` 外出分支设计上有等待与最终回应；不是普通轮重放 |
| 文字之后还有图、语音 | 附加表达；文字与表情合并，照片轮后单独发 |
| 用户回复附近又收到主动消息 | 比对心跳/时间触发的 TraceId；不能仅凭时间近认定为重复发送 |
| 消息或延迟照片发错聊天 | 优先检查触发 Moment 的会话载荷；当前已改为旧轮沿用原会话 |

去重是进程内的 30 分钟 / 4096 条有界缓存，跨进程重启或超出窗口不保证去重。没有有效 ID 时继续接收。不要盲目重试发送动作：超时可能发生在 QQ 已收到了消息之后。

## 收到图片但看不清内容（2026-09-17）

阶段日志由 `SoulRuntime.Emit` 发到控制台网页 `/events` 实时事件流，不写 Docker stdout；`docker logs | grep 识图` 无输出不能证明未执行识图。2026-09-19 工作区修复后，即使网页未打开，Host 也会在内存保留最近 300 条事件；打开/刷新/重连时回放，再接实时事件。Host 重启后历史清空，不是磁盘日志。

- `get_image｜unreadable-file,qq-cdn` 表示协议同时返回其他容器的文件路径和 CDN 地址；还会继续尝试 CDN，不能仅凭该行归因共享目录。
- `识图模型失败` 表示已取得非空图片候选并进入模型调用，不代表图片格式或供应商请求有效。旧版只记录异常类型；旧版 `识图完成｜chars=24` 实际可能是固定失败提示。
- 本次修复：入站 PNG/JPEG/GIF/WebP 按文件签名规范 MIME，覆盖 CDN 返回的 `application/octet-stream` 或错误类型；内联 Base64 同样规范并检查大小。无法识别且没有图片 MIME 的数据不再默认伪装 JPEG。
- 新日志显示模型客户端类型、模型名、图片数量和 MIME；模型失败保留脱敏、截断后的异常原因。已知 API Key、URL、Bearer 和内联图片数据做脱敏；排障仍只分享必要阶段行。失败和未配置分别记为“识图未成功”“识图未配置”，不再统称完成。调用方取消正常向上传播。

验证：新增 `Tools/ChatCheck/VisionTransportChecks.cs` 使用回环 HTTP 模拟 CDN 和模型服务，覆盖跨容器路径不可读、二进制/错误 MIME、错误页面、Gemini 原生与 OpenAI 兼容的实际请求体、HTTP 400 错误可见性与脱敏。`--vision`、完整 ChatCheck、`--prompt-layout` 通过；Host/ChatCheck 构建通过。没有调用真实模型或发送 QQ 消息。

本机 Gemini 已由用户实测成功，识图描述进入了后续回复。云端旧日志只显示 `InvalidOperationException`，没有状态码和具体错误；MIME 是源码中已修复的确定缺陷，不能据此宣布此次云端故障已解决。更新到 0.1.9 后保留云端原模型复测，查看具体错误。本机源码修复不会自动更新云端容器。

### 2026-09-19 后续定位

用户提供的新日志显示云端已取得两份 JPEG，并通过 `DeepSeekClientManager` 调用 Gemini 的 OpenAI 兼容中转；上游返回 HTTP 500 `upstream error: do request failed`，退避重试三次耗时约 32 秒。用户随后换 Kimi 识图成功。此证据将当次失败定位到模型调用阶段，不能归因于 NapCat 文件不可读，也不能证明模型本身无视觉能力。

确定修复：`OneBotPlatformAdapter` 会保留同一图片的 URL、缓存名等备用来源，旧 `VisionLogic` 将每个成功来源都加入请求，造成一张图重复上传。现在按图片字节的 SHA-256 去重，在独立图片计数达到四张之前继续加载；URL/Base64 标识采用区分大小写的比较。请求日志新增图片字节总数，去重日志仅报数量，不报图片内容。ChatCheck 用单个 QQ 图片段、两个不同 CDN 来源和跨容器路径模拟，核验两种协议最终都只有一份图片，也覆盖多个别名不会挤掉后续不同图片。

重复图片会增加请求大小与输入，但尚无证据证明其导致本次中转 500。更新云端后应看单图请求 `images=1`，并在相同供应商、模型、API 类型和图片下复测；若仍 500，继续核对云端供应商通道与上游错误。未自动切换模型或 API 类型，未访问真实模型做测试。

## 日志、说说与夜间余温（2026-09-19 工作区修复）

- `RecentEventLog` 在无订阅时也保留最近 300 条，回放与订阅在同一锁中完成，慢订阅也有界。前端收到连接握手后替换旧视图，避免重连重复。图片 Data URI、长编码串、换行与超长事件在缓存前处理，一条事件只占一行。
- 相机 `log_request_body` 兼容原配置键，但只打印模型及请求长度，不再打印正文或 Base64 的头尾片段。Host 入口另有编码过滤，覆盖其它日志路径。
- 空闲说说改为完整自然的一小段，表达具体心事及自己的感受/疑问，避免空泛意象；保留可以不发、不必有大事的语义。公开内容不照抄私聊及私密信息。空闲素材的内心和当天轨迹预算扩大，不修改空闲抽签或发布闸门。
- 夜间余温加入当天轨迹，事件从全天采样最多八件，每件保留更多上下文；引导解释自己的在意、理解变化或未解疑问，通常一到三小段。取消“她在睡觉”的默认场景，不以守夜、掖被子等动作代替感想；保留无内容可沉默、发送时窗和每日去重。未修改潜意识/身份复盘内部逻辑。

验证：Host、相机及空间插件构建均 0 警告/错误；完整 ChatCheck、`--vision`、`--prompt-layout` 与 `git diff --check` 通过。新增回放、并发、慢订阅、关闭订阅、编码过滤及全天素材回归。文字自然度、云端更新及 Gemini 真机复测尚未验证。

## 图文说说与清醒联系规划（0.1.10）

- 空间准备阶段返回正文与可选 `image_prompt`，不执行发布。中枢 `QzonePublishLogic` 调用相机 `dispatch=generate` 获取图片，再由空间上传并只提交一次图文说说，不额外发 QQ 私聊图片。相机不可用时只生成纯文字草稿；明确选择配图后若生成或上传失败，本次说说不发布。
- 空间使用 `cgi_upload_image` 的说说附件类型上传图片，校验图片字段后填入发布请求的 `richval`、`pic_bo` 等参数；接口格式参照实现者的[上传接口说明](https://github.com/Gu-Heping/onebot-qzone/blob/main/doc/photo-api.md)与[说说接口说明](https://github.com/Gu-Heping/onebot-qzone/blob/main/doc/emotion-api.md)。这是逆向接口，已用模拟 HTTP 验证请求/回包，尚未向真实空间试发。
- 成功、失败或取消后，清理归相机所有的本次临时图片。旧空间插件不会收到 `prepare` 请求，避免把准备误当发布；旧相机不支持 `release` 时不调用该分支。更新时 Host 与空间/相机 DLL 应一起安装。
- 清醒的空闲不再清掉心跳，已安排的心跳到期仍可唤醒。安静且漏填时间时使用 240 分钟兜底；普通聊天中明确填写的时间和方向也会落入调度，不被首次随机范围覆盖。睡下或手动关闭心跳仍清除安排。唤醒只重新考虑联系，并不保证每次发消息。
- 先保存下次心跳，再执行可能耗时的空闲生活动作；说说生成失败不会因此丢掉后续联系时间。已处于旧版空闲且没有任务的角色，在下一轮正常聊天后按新规则安排。

回归：`QzoneMediaChecks` 模拟纯文字、自主配图、固定正文、相机不可用、生图失败、上传失败、取消、发布回包不确定及旧插件；确认图文只发布一次、不额外私聊发图。`HeartbeatContinuityChecks` 使用真实 SQLite 和时间调度插件验证安静时的 0/90/240/480 分钟、普通聊天的显式时间、睡下与关闭心跳。所有网络操作均由模拟器接收。

## 不发照片

按顺序查，避免只改 Prompt：

1. **运行版本**：Host 和已安装 `qq-imagegen` DLL 是否都更新？编译 Host 不会安装外部插件。
2. **可用性**：QQ 已连接、回发开启、相机插件启用、生图供应商/模型/Key 配置齐全；只检查是否配置，不输出 Key。
3. **心智输入**：稳定段有相机说明与 `image` 字段；动态段有“相机此刻”。后者仅在生图器官可用时加入。
4. **选择**：看“心智判断完成”的 `image`。长期为无时，查看真实发图反馈是否存在、上下文是否适合分享。不要用固定概率强制拍照。
5. **映射**：看“外显图片路由”“后台生图已开始”。`qq.image.send` 只接 `file`，生图须走 `qq.imagegen.generate`。
6. **生成**：看画面规划、参考图、请求错误和“生图未成功，不发图”。供应商问题与未选择发图是两类问题。
7. **发送**：看“QQ 图片发送完成”的 status 与“后台图已发出/后台发图未成功”。发送失败不得伪造成功回执。

相机反馈读取当前会话最近 200 条运行事件内的照片回执，统计最近 80 条真实对话内后续的角色回应。没有记录只说明查询窗口没有，不能说从来没拍过。6 次文字回应是重新考虑分享的提醒阈值，**不是出图配额**。分享频率最终由心智模型和具体聊天决定，需要真聊观察。

## 本地验证与应用

在仓库根目录：

```powershell
dotnet build Tools/ChatCheck/ChatCheck.csproj --nologo
dotnet Tools/ChatCheck/bin/Debug/net8.0/ChatCheck.dll
dotnet Tools/ChatCheck/bin/Debug/net8.0/ChatCheck.dll --prompt-layout
dotnet build Tools/Host/TraceSoul2.Host.csproj --nologo
dotnet build ExternalPlugins/QqImageGen/TraceSoul2.Plugin.QqImageGen.csproj --nologo
```

应用时使用实际启动配置解析插件目录，备份并替换 `qq-imagegen/TraceSoul2.Plugin.QqImageGen.dll`，保留原 `plugin.json`、配置和图库。相机使用 PluginApi 1.3.0，与 Host 0.1.8 同批升级；正式 Release 已包含配套文件。

真人收发验收会产生外部消息；离线回归不启动真实 Host。用户自己启动后，观察普通聊天中照片是否自然出现、同一入站是否只处理一次；如仍异常，留取同一 TraceId 的阶段日志，不必导出整份私人聊天。
