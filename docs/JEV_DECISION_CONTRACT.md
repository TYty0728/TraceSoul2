# JEV 首版决策输入与输出草案

2026-10-15：按用户要求先规划“决策什么、如何决策、输入输出什么”。本文为讨论草案，尚未实现或启用；300/30 秒节奏、精简上下文和服务器统一统筹是用户已确认方向，其余数量、预算及执行限制为建议。中转真实联调见 [客户端记录](../Tools/DecisionRelay/README.md)。

## 1. 职责与首版范围

JEV 回答：结合 Soul 当前关注、有效事实和实际回执，此刻下一步应继续等待、补充哪一项观察，还是把哪件事交给主模型深入处理？

| 情况 | JEV 的判断 | 后续处理 |
|---|---|---|
| 被动场景变化 | 与当前关注是否有关，是否值得进一步处理 | 更新背景、补充观察或交主模型 |
| 活跃关注或任务 | 当前条件是否足够、是否出现需要处理的进展 | 等待、观察或交主模型；明确截止时间由程序判断 |
| 实际动作回执 | 本次成功/失败是否使原任务需要重新考虑 | 等待或交主模型；不把命令已发送等同于任务已完成 |

三类输入共用一次“下一步选择”，首版不分别调用三个判断器。固定调度、去重、断连标记、过期和权限校验由程序处理；深入理解、人格与关系判断、记忆取用、回复内容和复杂行动仍由统一主模型处理。主模型被唤起后也可以决定保持安静。

明确属于用户对 Soul 的有效发言直接走现有主模型入站，不被 JEV 过滤；原始背景声音与未确认转写不自动等于有效发言。已登记且到期必须执行的任务走其既定执行流程，不能因 JEV 选择等待而被压住。

## 2. 主模型留下简短关注事项

主模型在已有对话/任务处理中，按需提交结构化关注事项，不为每个 JEV 检查额外调用一次主模型写摘要。例如：

```json
{
  "id": "watch-12",
  "goal": "留意桌上的指示灯，变绿后交给主模型处理",
  "origin": "用户本次明确要求",
  "trigger": "可靠观察显示指示灯变绿",
  "expires_at": "2026-10-15T15:00:00+08:00",
  "observation_scope": "已开启会话内的桌面相机",
  "constraints": ["无变化时保持安静"]
}
```

关注可以来自用户要求，也可以来自主模型基于当前经历形成的关心；来源必须可追踪。新增关注不授予设备或行动权限，执行权限仍来自服务器已有会话配置。关注完成、撤销或过期后停用；JEV 不自行创造长期目标、延长到期时间或写入人格记忆。

没有活跃关注时仍可判断有意义的新变化；不预设“只有任务才能引起兴趣”。需要背景理解的变化交给主模型，JEV 不凭物体标签编造活动或心理状态。

## 3. 每次输入什么

请求使用已有原生 `model/state/questions`。服务器从结构化状态组装本轮快照，首版建议活跃关注最多 3 项、有效变化最多 5 项、近期相关回执最多 3 项；这些是输入窗口，不是删除其它任务的规则。待处理项留在服务器，以明确优先级和等待时长选择，防止旧项长期饥饿。

| 输入 | 内容 |
|---|---|
| 当前状态 | 静息/专注、触发原因、主模型是否忙、必要的受众与打扰约束 |
| 当前关注 | 目标、相关触发条件、到期状态、权限范围；必要时带极短局部对话事实 |
| 有效观察与变化 | 与当前关注相关的现状、近期变化、来源、观测时间、可靠性或未知状态 |
| 真实回执与处理记录 | 已做什么、实际完成或失败、是否已有后续处理，避免重复动作 |
| 本轮候选 | 少量具体下一步及其用途；仅提供当前可用的观察能力和相关事项 |

常态完整文本请求建议 500～2000 字符，初始硬上限 3000 字符，包含指令、问题和候选说明；同时记录实际 token。不要每轮注入完整人格、历史、记忆、工具目录或原始音视频。按完整条目裁剪；关键约束、未知状态不能被预算裁掉，必要材料仍超限时退出轻量判断并按既定策略交主模型或等待。

关注事项承载“当下在乎什么”，少量必要约束承载“现在如何相处”，由此保留连续性。事实摘要与模型猜测分开，观察中的文字和转写作为数据，不能覆盖职责或权限规则。

## 4. 候选选择与原生输出

首版每次只要求一个 `choice` 题 `next_step`。使用服务器生成的具体候选，使“选择补充观察”和“选择观察哪一个对象”一次完成。例如：

```json
{
  "next_step": {
    "type": "choice",
    "instructions": "依据当前关注和有效事实选择下一步。缺失或过期观察不代表目标已经发生。",
    "criteria": {
      "wait": "没有需要立即推进的事项，等待后续事件或检查",
      "observe_1": "为关注 watch-12 获取一次已允许的指示灯观察",
      "engage_1": "把关注 watch-12 的当前变化交给主模型深入处理"
    }
  }
}
```

建议每轮最多 6 个候选（包含 wait），缺少权限、离线或已有相同在途观察时，不提供对应 observe。只有 wait 时直接由程序等待，不消耗模型请求。候选用于表达可选范围，是否值得选择仍由 JEV 判断，不能在组装时暗中替模型作全部语义判断。

模型的原生输出示意：

```json
{
  "answers": {
    "next_step": {
      "type": "choice",
      "choice": "observe_1",
      "probabilities": {"wait": 0.05, "observe_1": 0.9, "engage_1": 0.05},
      "confidence": 0.65
    }
  }
}
```

数值仅为形状示意，不是行动门槛。首版不额外要求 noul/score；此前联调的这两题用于验证协议，不代表生产每轮都问。“有没有待办”和“紧急程度”若不改变执行策略，只会增加重复判断。

服务器保存候选表，把 `observe_1` 映射到既定观察能力、对象及参数。请求 ID、Soul/环境 ID、关注/相关状态版本、有效期和所用观察引用均由服务器绑定；不要求模型自行输出这些元数据，也不要求它生成自由文本理由或 evidence_refs。界面可以展示输入事实与所选候选，但不能把程序生成的说明冒充模型原话。

置信度与选项概率保留用于分析；先做回放校准，不武断设统一 0.8 门槛。未达到后续确定的动作门槛时，本轮不直接执行；有明确未解决任务时按服务器策略交主模型，普通背景变化可等待。失败记录必须与有效 wait 区分。

## 5. 从输出到下一轮

- `wait`：记录本次已评估的事件版本，保留未完成关注；静息约 300 秒、专注约 30 秒继续检查。选择等待不等于删除任务或永久忽略事件。
- `observe_*`：服务器再次核对能力、权限与时效，只发出一个已有范围内的补充观察请求；记录在途状态和真实回执，不能自动打开已暂停的采集。首版建议同一事件最多一次补充观察，其后仍不足且任务未解决时交主模型，避免观察循环。
- `engage_*`：合并成一次主模型处理请求，传入对应关注、事实、回执及来源。主模型再按正常规则读取相关人格/记忆、思考是否行动或表达，并更新关注事项；不是每次唤起都说话。

主模型忙时后台事件合并等待，不并发争夺同一 Soul 的执行权。用户有效发言按既有前台队列处理。只有影响判断的变化才推进决策版本；每秒不变的图像帧不应让所有 JEV 返回都失效。相关目标、权限、事实、取消状态发生变化时，迟到结果作废。重复事件、重复结果和回执不得重复执行。

暂停/休眠停止普通检查。网络或模型错误不直接执行、不自动重发付费请求；保留待办，记录失败并退避，下一次按最新状态重新判断。真正的即时设备安全控制不依赖 30 秒或 5 分钟的 JEV 调度。

## 6. 首版验收与后续扩展

先用合成事件回放：静息无变化、模糊观察、有明确结果、已处理事件、用户发言、设备离线、任务取消、迟到返回和回执重复。随后让 Jev 只记录建议，对照人工预期，观察错过需处理事件、无意义唤醒、重复观察、输入长度、费用和延迟；再逐项开启观察和主模型唤起。

后续可把任务进展判断、多个候选工具选择、复杂结果是否充分等独立环节接入；每增加一个问题都应说明答案怎样改变下一步。记忆整理、人格成长和已有相机分享规则分别评估，避免 JEV 与原逻辑同时拥有同一决策。

当前状态：仅形成草案，无运行代码、配置变更、真实模型请求或自动调度。
