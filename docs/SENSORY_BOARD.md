## 已确认的分工

```text
微雪开发板
  摄像头定时采图、麦克风采音、触摸/按键
          ↓ Wi-Fi：JPEG 图片、分块音频、设备状态
自建感官服务（自家电脑或服务器）
  人脸检测/身份比对、物体检测、时序状态、语音听写
          ↓ 有时间和置信度的观察、最终转写
TraceSoul 平台适配 → 既有心智与记忆
          ↓ 决定表达的文字、图片、视频、语音内容
自建媒体服务：语音合成、图片缩放、视频转换
          ↓ 适合板子的媒体、播放指令
微雪开发板：屏幕显示、喇叭播放、报告实际完成情况
```

这里的「本地」指自己部署的识别程序，可以在服务器上运行；不是要求 ESP32-S3 装下识图和听写模型。板子仍需完成驱动、编码/解码、缓存、联网及播放调度。

持续感知不等于每秒调用心智。原始画面约每秒传给感官服务处理，感官服务维护最新状态，向 TraceSoul 提交有意义的变化；用户语音按最终句子进入对话。原始音视频默认只作有界处理缓存，不自动成为长期记忆。

USB 当前承担供电、调试、烧录及最小输出闭环；出现 USB 串口不等于电脑已获得摄像头或麦克风流。正式媒体通道建议用 Wi-Fi，网络部分仍需开发。

## 视觉：从「识人和物体」到「发生了什么」

首版以约每秒一张 JPEG 为采集目标，先从 640×480 候选分辨率实测；屏幕分辨率不限制摄像头上传分辨率。以下是候选方案，尚未安装或在本机跑分：

| 能力 | 自建程序候选 | 输出边界 |
|---|---|---|
| 找到人脸 | OpenCV YuNet | 人脸框、关键点、检测分数 |
| 认出已录入的人 | OpenCV SFace 特征及相似度比对 | 匹配身份或未知；需要先录入并校准阈值 |
| 检测人、杯子、手机等物体 | YOLO 小型目标检测模型 | 模型支持类别的框、类别与分数 |
| 出现、持续在场、离开画面 | 检测结果加跟踪、连续帧确认和超时 | 基于可见范围的状态变化 |
| 特定动作 | 后续姿态模型、时序模型或明确规则 | 只支持单独验证的动作，不泛化为任意场景理解 |

依据：[OpenCV 人脸检测与识别](https://docs.opencv.org/4.x/d0/dd4/tutorial_dnn_face.html)、[YOLO 目标检测输出](https://docs.ultralytics.com/tasks/detect/)。模型及权重版本在实施时固定，运行性能以实际部署机器为准。

「看到了人和杯子」不能直接写成「他在喝水」；「没检测到人脸」不能直接写成「他离开房间」。需要把可见事实、规则推断和未知分开。开放式描述当前任意活动不属于首版小模型承诺；每秒一帧也可能漏掉短暂动作。

录入及人脸特征保存在感官服务的持久数据目录，板子不维护人脸库。单帧识人成功不自动证明现场只有本人，也不自动开放私密记忆。

工程上保持有界队列：识别跟不上时保留最新画面，丢弃过时待处理帧；带上设备、帧序号、采集时间、接收时间及观测有效期。断线、遮挡、模糊和过期分别报告，不能持续沿用旧的「有人在」结果。进入/退出等事件需要连续确认，阈值待实测。

## 语音：持续采音，服务端流式听写

板子采集音频并分块传给感官服务。首版可用单声道 16 kHz PCM16 验证，裸音频约 32 kB/s（256 kbit/s，不含协议开销），之后再按带宽和 CPU 余量考虑 Opus。

听写优先评估 sherpa-onnx 的中文流式模型：边收音频边产生临时文字，停顿后确认最终句子。临时文字可回显到屏幕，最终文字才作为一次用户发言交给 TraceSoul，避免同一句修订多次触发回复。候选依据：[sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)、[流式 Transducer 模型](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/index.html)。具体模型、硬件资源、准确率和延迟尚未确定。

持续监听会话不要求每说一句都重新唤醒。VAD 用来区分人声和静音，必要时保留短前置缓存避免截掉句首。是否加唤醒词或本人声纹是会话策略，独立于开放式听写能力。

第一版建议半双工：板子播放回复时暂不把麦克风音频送入对话，停止播放后恢复。这是首版实现范围，不满足同时说话打断的完整体验。后续全双工需要把播放参考信号接入 AEC 并验证真实回声、延迟及打断；不能仅因单麦克风就断言全双工不可能。乐鑫有 [AFE/AEC 前端](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/audio_front_end/README.html)，在该板固件上的兼容及效果尚未验证。

## 输出：文字、图片、声音、视频

| 内容 | 自建服务 | 板子 |
|---|---|---|
| 文字 | 下发文字、显示指令 | 中文字体、排版、字幕/滚动显示 |
| 图片 | 按屏幕尺寸缩放、转兼容格式 | 解码显示，候选 JPEG |
| 语音 | 按角色音色合成、转换采样格式 | 缓冲播放并报告开始、进度、完成/取消 |
| 视频 | 缩放并转换为板子可解码的短片或帧序列 | 首版评估低分辨率、低帧率播放；需单独实测 |

320×480 SPI 屏适合文字、图片和动画。视频首版可评估 MJPEG/JPEG 帧序列，不能直接承诺任意 MP4/H.264 或流畅全屏视频。即使识别移到服务器，摄像头采集、Wi-Fi、屏幕刷新、视频解码仍争用板子的资源；摄像和播放能否同时稳定运行必须测量，暂停采集时应明确上报。

语音和视频的实际播放回执回到服务端，发送指令成功不能等同于用户已经听到/看到。掉线后不盲目重播过期语音。

## 现有 TraceSoul 能复用什么

- [实时通话插件](../ExternalPlugins/RealtimeCall/README.md) 已有最终转写进入心智、回复文本下发、播放回执和打断代次的链路；当前不接收原始音频，不是现成的开发板媒体服务。
- 现有通话插件只声明 Unity、QQ 音频桥和 debug 传输。正式开发板需要自己的平台/身体适配，视觉观察不能伪装成用户说话。
- 工作区的 [LocalVoice](../Tools/LocalVoice/README.md) 是 Windows + NVIDIA GPU 的 Qwen3-TTS 服务代码，当前返回整段 WAV，尚非流式输出。它可作为语音输出候选，本轮未检查其运行状态，也不能直接当成远端服务器已经可用。
- 现有声纹过滤模块可评估复用；它不是 ASR，也不能可靠分离多人同时说话。
- 微雪摄像头、屏幕、音频、Wi-Fi 例程可作为硬件驱动基础。ESP-WHO 板上识人已退出当前主方案，不再为人脸模型占用板子内存。

## 现成固件优先与外出使用

2026-10-14 用户补充：优先复用微雪或小智现成方案，希望能带出门，后续自行配锂电池。终端开发先评估小智已适配的录音、播放、配网和摄像头链路，以及微雪 LVGL/外设例程，再补 TraceSoul 协议；不默认从零重写全部固件。

依据[微雪硬件说明](https://docs.waveshare.com/ESP32-S3-Touch-LCD-3.5)，本型号内置 2.4 GHz Wi-Fi 和 Bluetooth LE 5，无板载蜂窝通信模块或 SIM 卡槽。[小智项目](https://github.com/78/xiaozhi-esp32)支持部分带 ML307/EC801E 等模块的 4G 板型，不代表本板自带 4G。

外出首选建议是「开发板 → 手机 2.4 GHz Wi-Fi 热点 → 手机蜂窝网络 → 自建服务器」。手机只共享网络，不需要开发手机中转 App；识别与心智仍在服务器运行。BLE 配网不等于通过蓝牙获得互联网，若用 BLE 转发图片/音频，需要额外手机端和传输协议。独立蜂窝通信留待确有脱离手机需求时评估，不能直接套用其他板型固件。

板子主电池接口为 3.7V 锂电池 MX1.25 2Pin，AXP2101 支持充放电管理。选电池需核对接口正负极、尺寸及允许充电电流；续航需按实际摄像、传输、屏幕及播放负载测量。[微雪 FAQ](https://docs.waveshare.com/ESP32-S3-Touch-LCD-3.5/FAQ)当前说明 3.5-C 外壳不能容纳电池，具体外壳版本和空间仍需核对。本轮未配网、购买或连接电池。

### 首版完成后的体验

设备启动后显示连接状态。进入感知会话后，摄像头约每秒上传一张图片，服务端识别人脸与有限类别的物体；麦克风音频送服务端产生临时字幕，停顿后确认一句完整发言。TraceSoul 接收最终发言和近期有效观察，决定回复；设备显示文字、播放合成语音，也可显示下发图片。人在画面中持续不变不会每秒触发一次对话，识别不到时报告未知或超时。

首版采用半双工：播放回复时停止向 ASR 提交麦克风内容，播放结束后恢复。持续会话不要求每句话按按钮；屏幕提供明确的采集状态，以及暂停感知、停止播放入口。暂不承诺任意活动理解、全双工打断或流畅视频。

### 三部分代码与复用方式

| 部分 | 建议位置 | 职责与复用 |
|---|---|---|
| 板端固件 | `Tools/SensoryBoard/firmware` | 延续已验收的 ESP-IDF 固件，复用微雪外设驱动；参考小智同板型的配网、录放音、摄像头、界面组织。固定所用上游版本，不直接替换成连接小智云端的整套对话程序 |
| 感官服务 | 待新增 `Tools/SensoryGateway`，区分服务端入口与电脑 worker | 服务器管理设备连接、任务派发与最新观测；电脑 worker 运行识图/听写/TTS、返回结果。模型与录入资料在仓库外持久目录，电脑不决定 Soul 是否开口、行动或如何写记忆 |
| 身体适配 | 待新增 `ExternalPlugins/SensoryTerminal` | 注册物理身体及实际可用器官；映射最终转写、视觉观察、输出及回执。复用 RealtimeCall 的会话、代次、播放确认设计，避免复制一套心智或强行冒充 QQ/Unity 传输 |

`RealtimeCall` 当前只接 JSON 最终转写，不接原始音频；其身体声明为 App，传输枚举也没有该开发板。新适配需明确物理身体、设备绑定、受众和断连后的能力状态。视觉状态进入动态观察，不能伪装成人说的话。共享契约若需新增，更新 PluginApi 源清单并同步构建 Host 与相关插件。

### A. 终端基础与网络输出

- 将当前串行阻塞的接收/播放循环拆成通信、屏幕、音频任务，使用有界队列；播放不能阻塞心跳和停止命令。保留 USB 恢复与联调通道，同一时刻一个控制会话拥有输出权。
- 加设备 ID、每次启动的 boot ID、协议版本、实际能力、运行时长、可用内存和错误原因；状态可区分板子离线、网关离线、识别未就绪、正在采集与播放。
- 初次通过 USB 设置 Wi-Fi、网关地址和设备凭据；运行配置持久化，不编入源码。后续再补板上配网页，界面无需做文件管理器。
- 板子主动连接网关。控制及短音频走带鉴权的 WebSocket，公网用 WSS；相机 JPEG 独立 HTTP/HTTPS 上传，避免图片阻塞音频和心跳。图片输出先沿用已验证的 RGB565，后续按带宽需要增加板端 JPEG 解码。
- 每条命令带请求 ID、会话/代次和有效期；设备重连先报告状态，过期语音不重播。接收、开始执行、完成、失败、取消分别报告。USB 旧协议仅作为原型兼容入口，不把旧 `done` 冒充完整播放进度。

验收：网络发送中文、图片、短音频均得到设备回执；网关重启、网络短断、错误凭据、过期输出能按预期处理；连续运行至少 30 分钟，记录内存与重连结果。断电重启欢迎页与联网需另做实物验收。

### B. 相机与麦克风真实上行

- 相机先采一张实际 OV5640 JPEG，再测 640×480、约 1 fps。网关页显示实际采集画面、帧号、接收时间与延迟；过载只保留最新待处理帧，不积压过时画面。
- 麦克风先采一段并在电脑回放，确认采样率、声道、幅度、噪声和时长，再做连续分块。沿用当前 48 kHz I²S 时钟作为初始联调基线，服务端正确重采样到 16 kHz；确认输入/输出共享时钟约束后，再优化板端重采样或 Opus，不直接抽点降低采样率。
- 初始音频块以约 20～40 ms 为候选，队列有上限；缺块标明中断、重置当前识别段，不能把断线两侧拼成一句。原始媒体默认仅存有界内存，不自动录制。
- 短音频播放逐步改成流式缓冲，长回复不受现有 10 秒上限限制；缓冲不足、取消与尾音排空均有明确状态。

验收：实际镜头画面、实际麦克风录音分别通过；随后测持续上传与屏幕刷新、播放并行，记录采集是否暂停、丢帧/丢音和内存。远程期间可以验证链路与固定场景；真人说话、移动、遮挡和声学效果留待现场验收。

### C. 接现成小模型与当前状态

| 能力 | 首选评估 | 验收边界 |
|---|---|---|
| 人脸检测与比对 | OpenCV YuNet + SFace | 用户显式录入多角度样本后测试本人、未知人、侧脸、遮挡与不同光线；阈值通过实测校准，保留未知结果 |
| 物体检测 | YOLO 小型预训练模型 | 先支持权重已有类别；核对代码/权重许可并固定版本与校验值，记录 CPU/GPU 用时后再确定型号 |
| 中文流式听写 | sherpa-onnx 中文流式模型 | 临时字幕可修订，结束后只提交一次最终文本；以实际麦克风测试中文短句、停顿、噪声和连续会话 |
| 语音合成 | 可配置 TTS 适配；评估现有 LocalVoice | 现有 Qwen3-TTS 服务是整段 WAV，需实测合成耗时、角色音色及服务器资源；不承诺已具备流式首包能力 |

维护当前可见人脸/物体、最后观测时间与有效性。多帧确认后产生变化，短暂丢检不反复报告进出；断线或画面不可用立即让旧状态过期。不能从“杯子和人同时出现”直接断言“正在喝水”。人脸、声纹匹配不自动改变私密会话权限。

模型先做同一批实录样本的准确性与延迟比较再锁定；文档中的候选并不是安装承诺或已测性能。官方依据：[OpenCV](https://docs.opencv.org/4.x/d0/dd4/tutorial_dnn_face.html)、[sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/index.html)、[YOLO](https://docs.ultralytics.com/tasks/detect/)、[小智](https://github.com/78/xiaozhi-esp32)。

### D. 接入 TraceSoul 的观察、对话和表达

- 最终 ASR 是一次语音发言，绑定设备、说话者、会话和受众；视觉变化是有来源/时间/置信度的观察，两者分别接入。视觉状态持续更新不等于持续唤醒心智，具体唤醒门槛在接入时明确。
- 先以模拟核心验证事件与回执，再接真实 Host；不改核心人格、身份复盘和记忆整理规则来迁就设备。
- 同一回复的文字与语音共享输出 ID，但显示完成、音频播放进度各自记录；画面已显示不冒充语音已播放，设备离线不冒充执行成功。取消/断连只确认实际完成部分，重复回执不得重复入库。
- 回复通过该物理身体可用器官路由，设备断连即时撤下对应能力；不无条件把回复发到其它身体。恢复连接不自动重播旧回复。
- 复用既有声纹代码前需完成实录校准，并协调其当前“整段先校验再 ASR”的策略与流式临时字幕；不能假定直接拼接后天然支持本人流式转写。首版是否只接收本人声音单独配置。

验收：本人说一句 → 屏幕临时/最终字幕 → 核心生成回复 → 文字和声音 → 分别确认执行；重复请求、旧代次、断线期间和暂停采集期间不产生错误对话或回执。识人、最终转写和输出均可追踪来源。

### E. 外出与后续增强

验证手机 2.4 GHz 热点、蜂窝网络下 WSS/HTTPS、切网重连；完成音频压缩与图片限流后再评估持续外出使用。16 kHz PCM16 单声道仅上行约 115 MB/小时，48 kHz 约 346 MB/小时（连续发送、不含协议和图片），因此原始 PCM 只作联调基线，半双工/静音抑制/Opus 的实际流量需测量。

电池接入后补电量、低电提示与休眠/唤醒实测；安装前核对电池规格与极性。随后分别推进短视频/动画、回声消除和全双工，不能让这些能力阻塞首版感知对话。

下一次实现先补服务端设备/worker 会话契约及无副作用模拟，再推进 **A：网络输出 + 可诊断的终端基础**。网络与配置通道稳定后做 B；不在一次固件改动中同时塞入联网、相机、听写和核心接入。

### 已确认修订：服务器统筹与 JEV 决策

目标部署链路：

```text
开发板 ⇄ 服务器感官入口 ⇄ 家中电脑的识别/TTS worker
                 ↓ 带来源与有效期的观察、最终转写
          服务器精简状态 → JEV 轻量检查
                 ↓ 按需唤起统一主模型思考、行动与表达
          服务器下发文字/图片/语音 → 开发板回执
```

电脑 worker 主动建立到服务器的受鉴权连接，服务器按连接派发工作，不要求开放家中电脑端口。手机热点下的板子也连接服务器；电脑不可用时服务端明确标记对应识别/TTS 能力不可用。迁移小模型只改变 worker 位置，不迁移 Soul 的权威状态。当前 USB 桥仍可用于开发，但不因此在电脑另起一份 Soul。

服务器拥有：角色/会话/受众绑定、当前有效观察、重要性判断、唤醒与行动选择、记忆和状态提交、表达意图与设备输出授权。电脑拥有：有界媒体缓存、模型实例、流式识别中间状态，以及按已配置规则做重采样、VAD、重复帧合并等技术处理。识别结果必须带设备/任务/序号、时间、模型版本、置信度及未知/失败状态；电脑不能自行改写人格、长期记忆或替 Soul 发言。断线期间不提升为本地决策模式，不补放过期命令。

JEV 沿用项目现有“决策用途槽”的定义，可选供应商模型；不假定存在特定的“GPT JEV”官方型号。服务器发起模型请求、提供与本次判断有关的精简状态、验证结果并提交状态；推理可由所配置供应商承载。多个决策环节可以先共用一个 JEV 模型，不必先部署多个独立决策代理。

用户最新确认：主模型统一承担思考与表达，不再分开配置“开口/思考”；配置合并已在源码完成，尚未部署。JEV 静息约每 5 分钟、专注约每 30 秒检查一次，输入仅几百到几千字；初始建议常态 500～2000 字符、含指令和格式的完整文本请求上限 3000 字符。它读取当前任务、近期变化、必要约束与真实回执，不全量加载人格和记忆；需要深入处理时交给统一主模型。定时检查可以保持安静，有效用户发言立即进入正常入站流程。专注须有明确任务及有效期；休眠/暂停停止普通检查。该调度和预算尚未实现。

首批 JEV 接入点：

1. **被动观察的注意判断**：场景发生变化后，结合当前活动判断更新背景、请求补充观察或触发核心处理。普通有效用户发言仍须进入正常对话，不能被背景事件过滤静默吞掉。
2. **有限行动分流**：选择等待、请求会话已允许的补充观察，或交给主模型深入处理；查资料、回答及有副作用的行动先保留在统一主模型。是否调用额外视觉大模型必须另行配置，不能让每秒识图自动变成大模型调用。
3. **反馈后的调整**：依据真实成功、失败、离线或取消结果判断是否需要核心继续处理。复杂规划、关系判断、记忆取用与最终表达仍由主模型完成；具体身体/器官路由与执行资格由程序绑定和校验。

后续再评估把更多语义判断迁入 JEV，包括既有记忆整理中的候选判断；本阶段不自动重写人格、身份复盘、记忆写入或相机轮后分享的既有规则。每个环节明确唯一决策者，避免原 Agent 和 JEV 同时决定同一个行动。

JEV 输入使用服务器生成的精简快照与版本，输出有界结构化决策；每轮限制调用次数、耗时和可执行动作，迟到决策须核对上下文版本，必要时作废。观察连续不变不额外触发事件请求，仍保留定时检查；近邻变化合并，主模型忙时不并发争抢执行权。保留程序对权限、证据引用、能力、代次、重复操作和回执的校验；所有决策服从同一 Soul 的权威状态，不通过高频复制全部身份、关系和记忆实现一致性。

接入验收先使用录制/合成观察与模拟模型，检查注意判断、有效用户发言、不确定结果、worker 断线、重复事件、旧决策和动作副作用；再让真实 JEV 在只记录建议的模式中与现有行为对照，最后逐项启用执行。当前 JEV 只有路由已实现，以上环节均尚未接入。详见 [JEV 决策路由](JEV_DECISION_ROUTE.md)。
