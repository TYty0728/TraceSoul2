## 感官终端接入原则（规划）

- 服务器作为设备会话、有效观察、角色上下文和决策的权威来源；电脑作为识图、听写、TTS worker，主动连接服务器，按任务返回带来源/时间/版本/置信度的结果。迁移 worker 不改变 Soul 的决策位置。
- “广泛使用”指在多个语义判断环节引入 JEV，不表示每帧图片/每块音频都调用，也不必先建立多个独立代理。先共用明确配置的 `jev` 槽，按环节区分输入/输出契约与验证；不同模型分工待实测质量与延迟后再细化。
- 首批考虑被动场景变化的注意判断、补充观察/工具/表达的行动选择、执行反馈后的调整。普通有效用户发言仍沿正常入站回应约束处理，不允许被动事件过滤吞掉发言。
- 统一服从同一 Soul 的权威状态；高频 JEV 只接收与当下有关的精简事实和约束，不全量注入身份、关系、记忆。需要这些材料的判断交给主模型。已有决策迁出一个环节时，同时停用该环节的旧入口，避免双重行动；具体路由、权限和状态提交由程序完成。
- 注意判断新增阶段也计入全轮调用/时间预算；被动观察按变化合并。决策带上下文版本，执行前核对新事件和取消状态，不能让迟到结果作用于已经变化的场景。
- 先进行无副作用回放与只记录建议的真实模型对照，再逐项启用执行。记忆整理、身份复盘及相机轮后机会另按已有规则迁移，本阶段不以“增加 JEV”为由自动改写它们。

项目内部 `jev` 是决策用途槽，用户指定的实际候选服务为 TypeSafe Jev 和 OpenAI Decisions，原生协议适配状态见下节。服务器统一发起模型请求并掌握执行权，所选模型可由供应商 API 承载，不等于必须在服务器自托管该模型。感官终端完整部署与阶段验收仍在工作区草案中维护，将随终端实现另行提交。

### 0.1.46 的配置入口与能力

配置入口是 TraceSoul 主控制台的「大脑 · LLM」，不是开发板 USB 控制页。先在供应商管理填写接口类型、Base URL、Key 并添加实际模型 ID，再到默认用途槽选择 JEV 并保存。目前支持项目已有的 OpenAI 兼容聊天协议与 Gemini 原生协议；特定服务是否兼容须按实际文档核对。此处只选择模型，尚无 30 秒/5 分钟调度开关。

在 WebUI「大脑 · LLM → 默认用途槽 → JEV（决策）」选择已有供应商的文本模型，点击「保存槽位」。可与聊天使用不同供应商/模型，也可明确选择同一个模型。留空禁用；旧配置无需迁移。

- 槽名为 `LlmSlotNames.Jev`（`jev`），持久化在现有模型配置中。
- `GET /providers/slots` 返回 `jev: { providerId, model }`，公开投影不包含 Key。
- `PUT /providers/slots` 接受相同对象；空 `providerId` 清空，省略 `jev` 或传 `null` 保留原选择，兼容旧客户端。
- 删除供应商或所选模型会清空关联槽。`ResolveSlot("jev")` 与 `ResolveExplicitSlot("jev")` 均只使用明确配置，不按模型的用途标记自动回退。无 Key 返回 `null`。
- 宿主 `LlmProviderStore.CreateJevClient()` 创建隔离客户端，沿用所选供应商的协议、温度、思考开关、超时与代理；不使用复盘专用温度，不改变主对话客户端。
- 插件复用现有 `ILlmProviderDirectory`，先 `ResolveExplicitSlot(LlmSlotNames.Jev)`，再 `CreateClient(endpoint.ProviderId, endpoint.Model)`。未新增接口方法，不要求插件实现额外成员。

“配置完成”只代表路由可解析。当前 `AgentLoopLogic` 和相机插件仍使用既有流程；没有把 JEV 客户端自动挂入每轮聊天。

## 后续设计：高频轻量检查与按需深入处理

2026-10-15 在真实联调后形成 [首版决策契约草案](JEV_DECISION_CONTRACT.md)：关注事项 + 有效事实 + 回执作为输入，首版每轮一个原生 choice，从具体候选中选择等待、补充观察或唤起主模型。该文尚待讨论，不代表实现或用户已经确认所有细节；下面早期自由 JSON 输出建议以该草案中的原生答案与服务器元数据分离为后续方向。

以下类型、参数与调度均待实现。用户明确的节奏是静息约 300 秒、专注约 30 秒；精确预算与接口是实施建议。

```text
板端采集 → 电脑小模型 → 服务器有效观察与最终转写
                              ↓
           定时检查 / 被动关键事件 → 精简 JEV 判断
                                   ├─ wait：保持安静
                                   ├─ observe：补充允许的观察
                                   └─ engage_main：交给统一主模型深入处理
用户有效发言 ──────────────────────────→ 统一主模型
                                       ↓
                   按需加载相关上下文 → 思考、工具行动与表达
                                       ↓
                       程序执行、真实回执、权威状态更新
```

### 频率与触发

| 状态/触发 | 初始规则 |
|---|---|
| 清醒静息 | 约每 5 分钟一次 JEV 检查，即使没有新画面变化，也可检查已有关注是否到期。一次检查可以直接选择等待。 |
| 专注 | 约每 30 秒一次；必须有明确用户指令或主模型已提交的活跃任务/关注及有效期，完成、撤销或过期后回静息。画面里有人不自动等于专注。 |
| 有效用户发言 | 立即进入现有入站流程，不等下一个定时点，也不由 JEV 判定是否值得回答。 |
| 被动关键事件/执行完成 | 合并近邻事件后可提前检查；与定时检查共用去重和并发控制，避免同一事件两次唤醒。 |
| 休眠、手动暂停 | 停止普通定时检查，唤醒按既有明确策略处理；静息与休眠是不同状态。 |

间隔由服务器配置并执行，不让模型任意缩短。每个 Soul 的检查串行运行，处理一个具备明确受众与权限的环境快照；多环境不拼接私密内容。主模型忙时合并后台事件并等待其结束后的最新状态，不并发争抢执行权。错过的定时点不补跑；重启只安排新的下一次检查。具体事件合并窗口、请求超时与失败退避作为运行参数实测。

### 输入预算

建议常态 **500～2000 字符、完整文本请求上限 3000 字符**，符合用户“几百到几千字”的要求。此为初始预算，不是已实现指标；计数包括固定指令、动态内容、输出格式及字段说明，另记录实际 token 数，不能将中文字数等同于 token 数。高频请求不附原始图像/音频。

| 内容 | 内容边界 |
|---|---|
| 固定规则和输出约定 | 极短的职责、等待/补充观察/请求主模型定义与事实约束；稳定前缀保持稳定。 |
| 当前任务和模式 | 正在关注什么、为何专注、何时到期、当前受众与必要限制。 |
| 近期变化及仍有效事实 | 人物在场变化、物体变化、必要短转写，附来源、时间和不确定性；不复制历史流水。 |
| 最近动作与结果 | 未完成事项、实际成功/失败、是否已回应、暂时不可用的设备。 |
| 可选观察 | 仅当下可用的少数观察 ID 和简短用途，不塞入完整工具目录或大段参数 schema。 |

不默认注入整个人格档案、身份卡、关系史、长期记忆召回、完整聊天历史或每帧识别清单。服务器直接从结构化状态选择材料，不为每次检查额外调用模型写摘要。必要约束由服务器保留且执行时再次校验；涉及关系、价值判断、记忆解释或信息不足时，交给主模型读取所需材料。这样共享同一 Soul 的状态，不需要高频重复加载全部人格。

超过预算时优先移除过时、重复和低价值观察，保留关键约束、当前任务与真实回执；按完整条目裁剪，不截断 JSON 或事实句。仍装不下时显式报告上下文不足，交给主模型或等待，不能悄悄丢掉必要约束。新感知缺失时保留“未知/离线/已过期”，不将旧画面当成当前事实。

### 最小结果与权威边界

早期候选接口为 `IJevAttentionPlanner.DecideAsync(JevAttentionRequest, CancellationToken)`，尚未实现。原生协议明确后，不再要求模型生成带 reason/evidence_refs 的自由 JSON；建议由原生 `answers.next_step.choice` 选择本轮具体候选，服务器绑定环境、相关状态版本、来源引用和具体观察参数。完整输入输出与关注事项见 [首版决策契约草案](JEV_DECISION_CONTRACT.md)。

`observe` 仅能请求当前会话已允许的补充观察，不自动开启已关闭的摄像头或麦克风，不发送文字/语音；`engage_main` 只提交一次核心处理请求，不直接代写回复、人格、记忆或任意系统提示。程序核对引用、能力、上下文版本、请求有效期和已处理事件，执行后登记真实回执。主模型继续拥有完整的思考、行动与表达能力；不把它缩减成润色器，也不让两个模型同时决定同一动作。

“广泛使用 JEV”后续可扩展到任务进展、观察充分性、工具结果分流等有边界的判断，各环节分别给短输入与可验证输出。涉及复杂任务规划时按需调用，不把完整工具参数和全部记忆带入每 30 秒的检查。是否迁移拍照等已有语义判断，单独确定唯一入口与验收；现有相机轮后机会和镜头规划暂时保留。

### 失败、诊断与实施顺序

- JEV 未配置时不启用新检查，保留现有主模型流程。调用失败或输出无效时不执行动作；有界纠错与重试计入同一调用/时间预算，持续失败退避并报告，不悄悄改用其他模型。
- 决策返回前有新发言、任务变化、暂停或离线时，重新检查版本并丢弃失效建议。已受理的动作不重放；受理/运行中不等于已经看到或听到。
- 记录触发来源、模式、下一次检查、输入字符数/token、耗时、结果、校验失败和实际回执。普通日志不含密钥或完整私密上下文；控制台可解释为何唤醒或保持安静。
- 先实现精简输入构造、预算与结构校验，用模拟时钟/模型检查 300/30 秒切换、到期、事件合并、暂停、重启、慢响应、超时与不重复执行；再做只记录建议的真实模型对照，最后接入核心处理请求。模型质量、时延和调用费用在真实对照时测量。
